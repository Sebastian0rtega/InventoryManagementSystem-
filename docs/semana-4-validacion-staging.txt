2. OBTENER EL COMPOSE DEL COMMIT APROBADO

Sustituir <SHA> por el SHA completo con workflow verde y las imagenes publicadas:

  sudo mkdir -p /opt
  sudo chown "$USER":"$(id -gn)" /opt
  cd /opt
  git clone https://github.com/Sebastian0rtega/InventoryManagementSystem-.git InventoryManagementSystem-
  cd InventoryManagementSystem-
  git fetch origin dev
  git checkout --detach <SHA>
  test "$(git rev-parse HEAD)" = "<SHA>"

En despliegues posteriores, actualizar el clon existente con git fetch y
git checkout --detach <SHA>; no sobreescribir archivos del servidor a mano.

3. SECRETOS Y ACCESO AL REGISTRY

Crear el archivo solo en la instancia. backend/.env esta excluido del contexto
Docker por backend/.dockerignore; no agregarlo al repositorio, a una imagen, ni
a los logs. Reemplazar todos los valores de ejemplo por secretos de staging.

  cp backend/.env.example backend/.env
  chmod 600 backend/.env
  nano backend/.env

Usar credenciales de staging unicas y un JWT_SECRET aleatorio y largo. No pegar
secretos en este documento ni en comandos guardados en el historial.

Si GHCR requiere autenticacion, iniciar sesion con un token que tenga solo
read:packages; no guardar el token en el repo ni en el documento:

  read -s GHCR_TOKEN
  printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u <USUARIO_GITHUB> --password-stdin
  unset GHCR_TOKEN

Configurar las dos referencias inmutables de esta entrega en la sesion:

  export DEPLOY_SHA=<SHA>
  export API_IMAGE="ghcr.io/sebastian0rtega/inventorymanagementsystem:${DEPLOY_SHA}"
  export MIGRATE_IMAGE="ghcr.io/sebastian0rtega/inventorymanagementsystem:${DEPLOY_SHA}-migrate"

Comprobar la configuracion sin mostrar el contenido de .env:

  docker compose --env-file backend/.env config --images

4. DESPLIEGUE CONTROLADO

Antes del cambio, registrar la imagen API actualmente desplegada. En el primer
despliegue, registrar "ninguna":

  docker compose --env-file backend/.env ps
  docker inspect --format='{{.Config.Image}}' "$(docker compose --env-file backend/.env ps -q api)"

Si ya existe una API, verificar su liveness y readiness antes de continuar:

  curl -i http://localhost:3000/api/health
  curl -i http://localhost:3000/api/health/database

Descargar la imagen de API y la imagen de migracion construidas por CI. No usar
build en staging: el contenedor nuevo debe ser el artefacto publicado por CI.

  docker compose --env-file backend/.env pull api migrate
  docker compose --env-file backend/.env up -d --no-build database

Esperar y confirmar que PostgreSQL esta healthy antes de migrar:

  DB_CID="$(docker compose --env-file backend/.env ps -q database)"
  for attempt in $(seq 1 30); do
    DB_HEALTH="$(docker inspect --format='{{.State.Health.Status}}' "$DB_CID")"
    [ "$DB_HEALTH" = healthy ] && break
    sleep 2
  done
  test "$DB_HEALTH" = healthy
  docker compose --env-file backend/.env ps

Ejecutar las migraciones como tarea explicita ANTES de reemplazar la API:

  docker compose --env-file backend/.env run --rm --no-deps migrate

Si la tarea falla, detener el despliegue; no actualizar la API hasta resolver el
error. Las migraciones deben ser compatibles con la version anterior de la API.

Actualizar la API al tag SHA de CI y esperar su healthcheck (readiness):

  docker compose --env-file backend/.env pull api
  docker compose --env-file backend/.env up -d --no-build --no-deps api
  API_CID="$(docker compose --env-file backend/.env ps -q api)"
  for attempt in $(seq 1 30); do
    API_HEALTH="$(docker inspect --format='{{.State.Health.Status}}' "$API_CID")"
    [ "$API_HEALTH" = healthy ] && break
    sleep 2
  done
  test "$API_HEALTH" = healthy
  docker compose --env-file backend/.env ps
  curl --fail http://localhost:3000/api/health
  curl --fail http://localhost:3000/api/health/database

Verificar que el contenedor ejecuta el SHA aprobado:

  docker inspect --format='{{ index .Config.Labels "org.opencontainers.image.revision" }}' "$API_CID"

El valor debe coincidir con DEPLOY_SHA. Guardar tambien el identificador de
imagen anterior obtenido antes del cambio para el procedimiento de rollback.

5. ROLLBACK

No ejecutar migraciones down ni revertir cambios de datos destructivos a ciegas.
Las migraciones deben seguir una estrategia compatible hacia atras (expandir,
desplegar, migrar trafico y retirar columnas incompatibles en otra entrega).
Si la nueva API no pasa readiness, volver solo a la imagen anterior mientras
el esquema siga siendo compatible:

  export API_IMAGE="ghcr.io/sebastian0rtega/inventorymanagementsystem:<SHA_ANTERIOR>"
  docker compose --env-file backend/.env pull api
  docker compose --env-file backend/.env up -d --no-build --no-deps api
  docker compose --env-file backend/.env ps
  curl --fail http://localhost:3000/api/health
  curl --fail http://localhost:3000/api/health/database

Si la migracion no es compatible o hubo perdida/corrupcion de datos, no intentar
un downgrade automatico: mantener la API detenida si corresponde, preservar
evidencia y seguir el procedimiento aprobado de restauracion del backup de DB.
Registrar el incidente, el SHA anterior y el resultado del rollback.
